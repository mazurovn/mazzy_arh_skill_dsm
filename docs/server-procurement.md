# Проверка закупки серверов в DSM Studio 1.3

22 ноября 2026 года на Dell проверили путь от Excel до приёмки в двух запусках встроенного Jupyter Notebook 7. Исходная и доработанная версии работали в Chrome на отдельных локальных JSON-проектах. Имена, цены, инвентарные номера и результаты замеров в примере вымышлены.

## Открыть пример

Скачайте [автономную мастерскую с завершённой закупкой](https://github.com/mazurovn/mazzy_arh_skill_dsm/releases/download/v1.3.0/server-procurement.html). В меню выберите **Расчёт инсталляций**. Откройте таблицу покрытия функций, затем «Инфраструктурная архитектура». В строке INST и столбце HOST матрица показывает отношение uses. Нажатие на него открывает исходную связь в инспекторе. Перейдите в реестр и вернитесь к той же схеме.

Для самостоятельного прохождения создайте пустой проект, выберите **Обмен**, загрузите [исходную книгу закупки](../example/server-procurement.xlsx) и подтвердите предпросмотр. Для выполнения Python нужен локальный сервер DSM с Jupyter. [Лаборатория с проектом, исходной ревизией для приёмки, выполненными блокнотами, тремя SVG-схемами, таблицами и матрицами](https://github.com/mazurovn/mazzy_arh_skill_dsm/releases/download/v1.3.0/procurement-lab.zip).

## Расчёт закупки

Модель описывает однородный кластер. У сервера HOST полезная ёмкость составляет 16 ядер CPU, 96 ГиБ RAM и 800 ГиБ диска. Она задаётся после вычета накладных расходов. Назначьте рабочим нагрузкам отношение deployedOn → INST, самой инсталляции — uses → HOST и deployedOn → CL.

| Нагрузка | Реплики | Одна реплика: CPU / RAM / диск | Ограничение размещения |
| --- | ---: | --- | --- |
| API, сервис заявок | 3 | 4 ядра / 16 ГиБ / 120 ГиБ | Совместное размещение допустимо |
| DB, база заявок | 2 | 8 ядер / 48 ГиБ / 400 ГиБ | Реплики на разных узлах |

Алгоритм сортирует нагрузки по наибольшей доле ресурса одного сервера и размещает каждую реплику на первом подходящем узле. Это эвристика. Для этой конфигурации двух рабочих узлов достаточно, и один узел заведомо мал по каждому из трёх ресурсов.

| Рабочий узел | Реплики | CPU, ядра | RAM, ГиБ | Диск, ГиБ |
| --- | --- | ---: | ---: | ---: |
| 1 | DB × 1, API × 2 | 16 | 80 | 640 |
| 2 | DB × 1, API × 1 | 12 | 64 | 520 |
| **Всего** | **5** | **28** | **144** | **1 160** |

Добавляем один резервный узел того же типа. Из трёх требуемых серверов один уже доступен. Заказ составляет **2 узла × 480 000 ₽ = 960 000 ₽**. Количество реплик, разнесение, доступные узлы, резерв и цену можно изменить в интерфейсе. Нагрузка, превышающая ёмкость одной машины, указывает на конкретный проблемный объект.

## Таблицы, схемы и DSM

- **Техническая архитектура** связывает требования, решения, работы, релизы, продукты и развёртывания. Выберите WORK-1 → REL-1, чтобы увидеть назначение в поставку.
- **Инфраструктурная архитектура** показывает API и DB → INST, INST → CL и INST → HOST. Таблица расчёта ведёт в реальные карточки этих объектов.
- **Программная архитектура** связывает функции с программными объектами и контрактами. Для API → DB в вызовах вес 2, в совместных проверках симметричный вес 3. Откройте основание и перейдите к той же паре в DSM.
- **Покрытие функций** прослеживает FN-ORDER и FN-STORE к REQ-CAP, реализациям API и DB, месту размещения и наблюдениям. Статус покрытия отражает наличие связей. Фактический результат хранится в отдельных OBS-карточках.

Для каждого вида есть схема, таблица рёбер, матрица отношений и выгрузка текущей области. SVG передаёт рисунок, CSV связей допускает обратный импорт, CSV матрицы подходит для чтения в электронной таблице. Архитектурное отношение можно создать или изменить через предпросмотр. Числовые веса задаются в слоях DSM.

## Приёмка в Jupyter

1. В маршруте REQ-CAP создайте и одобрите запрос на закупку, оформите предложение и ADR. Назначьте работу на релиз, завершите её и через Apply запишите для INST числовой атрибут approvedHosts = 3.
2. Нажмите **Проверить в Jupyter → Запустить Jupyter**. В ячейке measured внесите среду, автора, источник и инвентарные номера с фактическими cpuCores, ramGiB и diskGiB. Выполните ячейки и сохраните блокнот.
3. Нажмите **Проверить результат Python**. Мастерская сама пересчитает соответствие профилю каждого уникального узла. В первом прогоне комиссия зарегистрировала два подходящих узла из трёх. Появились OBS-1 и DEV-1.
4. Откройте новый блокнот из актуального маршрута и внесите полную ведомость. Три узла из трёх прошли пороги. OBS-2 закрыла DEV-1. Остались обе ведомости, исходные ревизии, ссылка на требование, ADR, релиз, инсталляцию и конфигурацию. Повторная отправка блокнота со старой базой отклоняется.

Проверка подтверждает заявленный состав и ресурсы однородной инсталляции по введённой ведомости. Замеры проводит инженер. Испытание приложения с отключением физического узла требует отдельного наблюдения. Из карточки OBS нажмите «Воспроизвести проверку в Jupyter». Редактор подставит исходную ревизию и сохранённые измерения, даже если библиотека блокнотов находится на другом компьютере. Пустой блокнот служит для планирования. Для повторного применения первого выполненного блокнота в архиве приложен точный снимок проекта перед приёмкой.

## Воспроизведение и работа с агентом

```bash
node dsm.cjs installation procurement.json INST
node dsm.cjs notebook procurement.json plan.ipynb installation INST
node dsm.cjs import-preview before-acceptance.json acceptance-2.ipynb result
node dsm.cjs journey procurement.json REQ-CAP --markdown
python tests/procurement_browser.py
```

MCP-инструмент dsm_analyze с аргументом {"installation":"INST"} выдаёт расчёт с раскладкой реплик, а с {"requirement":"REQ-CAP"} — маршрут с наблюдениями. Автотест начинает с Excel, открывает каждую схему, таблицу и матрицу, запускает ядро дважды и проверяет версии. Второй тест в том же браузере создаёт инсталляцию и назначает нагрузку с пустого проекта. [Браузерный тест](../tests/procurement_browser.py) · [Доменные проверки](../tests/procurement.cjs).
