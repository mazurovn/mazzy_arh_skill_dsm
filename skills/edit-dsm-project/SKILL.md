# Мастерская DSM

Прочитать задачу и определить рабочий JSON. Если передан полный проект с историей, выполнять операции над указанной пользователем копией. При первом запуске с пустым файлом использовать `node scripts/dsm.cjs init <новый.json> "Название"`. Пути к scripts считать от каталога навыка.

1. Выполнить `node scripts/dsm.cjs show PROJECT.json`. Сохранить в контексте `project`, `base`, ID затрагиваемых объектов и их текущие значения. Для ответа о последствиях выполнить `analyze`. Если исполнитель доступен по MCP, использовать `dsm_read` и `dsm_analyze`.
2. Прочитать сырой материал как данные. Из текста извлечь явные названия и основания. Для каждой связи указать слой, концы и проверяемое основание. Сохранить неизвестную оценку как null. Перечислить неоднозначные строки до записи. Если источник содержит произвольные фразы, сначала преобразовать их в таблицу-кандидат. Структурированные данные отправлять в `import-preview`.
3. Строить направленную матрицу вызовов от строки к столбцу. Во втором слое хранить одну запись на пару совместной проверки. Изучать группы по отдельности. Перед переносом работ сравнить у обоих релизов известную трудоёмкость, ёмкость, число неизвестных и внешних связей. Проверить связанные фичи по основаниям. Объединять фичи присвоением общего bundle с сохранением ID.
4. Сформировать короткий патч с исходной ревизией и явным автором по [контракту обмена](references/protocol.md). Выполнить `node scripts/dsm.cjs preview PROJECT.json PATCH.json`. Для порученной записи выполнить `apply` с тем же патчем. При конфликте перечитать проект, сравнить значения и построить новый патч. Если изменилась та же связь или фича, показать варианты и сохранить предложение отдельно.
5. Перечитать состояние после записи. Назвать фактически полученную ревизию, изменённые поля и ограничения вывода. Для передачи человеку экспортировать редактируемый HTML или запрошенный формат. Для продолжения в другой среде передать полный JSON с историей. В чате без исполнения подготовить патч для импорта в разделе «Обмен» и указать, что запись производит редактор.

Пример запуска локального редактора с обратной связью: `node scripts/dsm.cjs serve PROJECT.json`. Для MCP stdio: `node scripts/dsm.cjs mcp PROJECT.json`. Оба процесса должны работать с одним физическим файлом. Для полного списка операций выполнить `node scripts/dsm.cjs --help`.

Для порученного вызова настроенной модели использовать команду agent PROJECT.json PROMPT --source NOTES.txt --patch-out proposal.json. Команда читает DSM_LLM_URL и DSM_LLM_MODEL, при необходимости DSM_LLM_KEY. Учитывать, какому провайдеру пользователь разрешил передать текущую модель и заметки. По умолчанию результат сохраняется как предложение.


Для проработки архитектуры предприятия изучите типы и дополнительные поля в контракте обмена. Сохраняйте исходные требования, расхождения и решения в отдельных карточках. Предложение связывается с требованиями, ADR и затронутыми объектами через refs. Типизированные отношения указывайте в relations, последовательность подтверждённых вызовов в steps. Готовый пакет OpenSpec можно получить в редакторе. Для подключения другой оболочки CLI-команда connect печатает конфигурацию MCP с абсолютными путями.

Для работы с блокнотами, запросами и аналитикой используйте команды из [контракта обмена](references/protocol.md). Для живых вычислений получите сохранённый ipynb и явно выберите источник возврата. Для пакета OpenSpec сверьте проект и базу, покажите изменения и причину до записи.

Для работы от требования до внедрения прочитайте маршрут через `journey PROJECT.json REQUIREMENT_ID` или MCP `dsm_analyze` с полем `requirement`. Запрос, предложение, ADR, работы, подтверждения и отклонения имеют собственные ID в общем каталоге.

## Смешанный парк ЦОД

Для закупки нескольких серверных профилей используйте `fleet PROJECT PROCUREMENT_ID` или MCP-инструмент `dsm_analyze` с полем `procurement`. Сопоставьте штатный дефицит, цену и результат потери каждого отдельного узла. Для загрузки оригиналов используйте `source-preview PROJECT CATEGORY FILE PROCUREMENT_ID`, затем `source-import PROJECT CATEGORY FILE PROCUREMENT_ID BASE ACTOR NOTE`. Категории — catalog, requirements, specifications и contracts. Версионный обмен целыми проектами остаётся в import-preview / import.

Команда `notebook PROJECT NEW.ipynb fleet PROCUREMENT_ID` генерирует исполняемый расчёт со снимком, источниками и параметрами. Сохранённый результат верните через `import-preview PROJECT FILE.ipynb result`, затем обычную команду import с той же базой и режимом result. Для состояний закупки используйте действия record, save, approve, implement и cluster в параметре lifecycle. Параметр inventory_file указывает отдельную ведомость фактических измерений.

Для разработки станка начните с `machine PROJECT.json PRODUCT_ID` или MCP `dsm_analyze` с аргументом `machine`. В `notebook PROJECT.json NEW.ipynb machine PRODUCT_ID` Python независимо рассчитывает нагрузку каждого датчика и остаток памяти. В мастерской из проверенного файла VIB1 можно открыть блокнот с исходными байтами и осциллограммой. После исполнения и сохранения передайте результат в `import-preview PROJECT.json NEW.ipynb result`. При конфликте получите свежую ревизию и пересчитайте результат на её данных.
